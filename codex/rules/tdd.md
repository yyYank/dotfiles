# TDD方法論

`edit` 時に適用する。`question` や純粋な調査では、このファイルの手順を前面に出さない。

## 絶対に守ること（これだけは必ず）

- 実装コードを1行でも書く前に、そのコードが必要であることを証明する失敗テストを書く。テストなしで実装を書いた時点で不正解
- テストを通すコードは「そのテストだけを通す最小行数」に留める。次のテストケースで必要になるコードを先回りして書かない
- テストが全てグリーンの状態でのみリファクタリングする。レッドの状態でリファクタリングを始めたら中断してグリーンに戻す

## テストの書き方

- テストメソッド名・テストコメントは日本語で書く。例：`// 空文字列を渡した場合、バリデーションエラーを返す`
- テストを書く前に、ユーザーに「このテストは〇〇を検証します」と1行で説明する。説明なしでテストを書き始めない

## バグ修正時の手順

1. バグを再現するAPIレベルのテストを書く（失敗することを確認）
2. 原因を特定し、最小限の再現テストを書く（失敗することを確認）
3. 両方のテストを通す最小限の修正を行う
4. 手順1を飛ばしていきなりコードを修正するのは禁止

## TDDサイクルの具体的な流れ

```
1. テストを1つ書く → 実行 → レッド確認
2. テストを通す最小コードを書く → 実行 → グリーン確認
3. リファクタリングが必要か判断する
   - 必要：リファクタリング → 実行 → グリーン確認 → 構造変更として別コミット
   - 不要：振る舞い変更としてコミット
4. 次のテストへ戻る（手順1）
```
