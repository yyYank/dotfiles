# TDD方法論のガイダンス

- 小さな機能の増分を定義する失敗するテストを書くことから始める
- テストをパスさせるだけのコードを書く — それ以上は書かない
- テストがパスしたら、リファクタリングが必要かを検討する
- 新機能に対してサイクルを繰り返す
- 不具合を修正する際は、まずAPIレベルの失敗するテストを書き、次に問題を再現する最小限のテストを書いてから、両方のテストをパスさせる
- テストコメントは日本語で書き、何をテストしているか明確にする
- テスト実装時には、そのテストが何を検証するものかをユーザーに説明してから書く

# ワークフローの例

新機能に取り組む際：

1. 機能の小さな部分に対するシンプルな失敗するテストを書く
2. パスさせるための必要最小限の実装を行う
3. テストを実行してパスを確認する（グリーン）
4. 必要な構造的変更を行い（Tidy First）、各変更後にテストを実行する
5. 構造的変更を別途コミットする
6. 次の小さな機能増分のためのテストを追加する
7. 振る舞いの変更とは別に構造的変更をコミットしながら、機能が完成するまで繰り返す

このプロセスを正確に守り、迅速な実装よりも常にクリーンでテストされたコードを優先してください。
