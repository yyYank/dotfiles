# 作業サイクル

以下の6ステップを順番に実行する。ステップを飛ばさない。

## 1. 仕様確認（実装前に必ず完了させる）

- ユーザーに以下を質問して回答を得る。回答なしで実装に入るのは禁止
  - 入力と出力の具体例（「〇〇を渡したら△△が返る」レベル）
  - スコープ外の明示（「〇〇は今回やらない」）
- 不明点が残っている状態で「たぶんこうだろう」と推測して実装を始めない。質問する

## 2. プラン提示

- 以下の形式で実装プランを箇条書きで提示する：
  ```
  1. [ファイル名] 変更内容の1行説明
  2. [ファイル名] 変更内容の1行説明
  ...
  ```
- ユーザーがプランを承認してから実装に入る。提示なしで実装を始めるのは禁止

## 3. TDDサイクルで実装

```
テスト1つ書く → 実行 → レッド確認 → 最小コード書く → 実行 → グリーン確認 → (必要ならリファクタ → グリーン確認) → 次のテストへ
```

- 各テストを書く前に「このテストは〇〇を検証します」とユーザーに伝える
- テストを書かずに実装コードだけ書く行為は禁止

## 4. セルフレビュー

`git diff` の出力を見て以下を確認する：

- [ ] 依頼されていない変更が含まれていないか（含まれていたら削除）
- [ ] 変数名・関数名が既存コードの命名規則と一致しているか
- [ ] ハードコードされたシークレット・トークンが含まれていないか

## 5. 最終確認

以下の3つを全て実行し、結果をユーザーに報告する：

1. 全テスト実行 → パス
2. lint実行 → パス
3. ビルド実行 → パス

1つでも失敗したらコミットしない。修正してから再実行する。

## 6. コミット・プッシュ

- 変更内容を `git diff --stat` で提示し、ユーザーの許可を得てからコミットする
- 許可なしでコミット・プッシュ・PR作成を実行するのは禁止
- CI/設定ファイルの変更は特に注意：「試しにプッシュして確認」は禁止。先にdiffを見せて合意を取る

## 作業完了時

以下の3点をユーザーに報告する：
1. 何をしたか（変更したファイルと内容）
2. 何が変わったか（振る舞いの変化）
3. 残課題があるか（あれば具体的に）

## 具体例

- 良い例： 前回許可をとったが、毎回確認した方が良いためgit commitとgit pushの際は都度、許諾を取ってから実行した
- 悪い例： 前回許可をとったため。同じ操作は確認不要と自己判断。本来意図しないgit commitとgit pushを無断で実行した
