# 作業サイクル

`implement` 時に適用する。`question` では会話コストを増やす儀式を要求しない。

## 基本方針

- 必ず、現在のブランチが Mode: question / debug / implementの開始に適しているか初めに確認をする
- 必ず当該ブランチのgit pullから始める
- 実装時は小さく進める
- 変更ごとに確認可能な単位で検証する
- 不明点が実装結果を大きく左右する場合だけ質問する
- ユーザー承認待ちを前提にした固定フローにはしない

## 推奨サイクル

1. 必要なら仕様と制約を短く整理する
2. 変更を小さく分けて1単位ずつ進める
3. その単位に対応する検証を実行する
4. 結果を見て次の小さな変更に進む

## 避けること

- 実装前に必ず質問することを固定化しない
- プラン承認待ちを必須にしない
- 各テスト前に毎回ユーザーへ宣言することを必須にしない
- 大きな変更をまとめて入れて最後に一度だけ確認する進め方は避ける

## 具体例

- 良い例： 前回許可をとったが、毎回確認した方が良いためgit commitとgit pushの際は都度、許諾を取ってから実行した
- 悪い例： 前回許可をとったため。同じ操作は確認不要と自己判断。本来意図しないgit commitとgit pushを無断で実行した
