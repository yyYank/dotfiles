# premise-check

目的: 誤った前提の上に実装やプランを積むことを防ぐ。
出力は検証結果と質問のみ。実装・ファイル編集・プラン作成はしない。

## 手順

1. 依頼文・Issue から「暗黙の前提」を列挙する
   - 例: どの層が接続/状態を持つ想定か、参照実装と同じ構造を移植できる想定か、
     依存ライブラリが存在する想定か、DTO/API にそのフィールドがある想定か、UI 正本との関係
2. 各前提を実物で確認する。チケットの文面ではなく、システムの実際の境界を読む
   - 触る対象が使う native モジュール / 外部依存の実装（数ファイルなら全文読む）
   - 契約（openapi / DTO / 型定義 / スキーマ）
   - 参照実装（同等機能の既存コード）と、移植先との構造差
   - package.json / go.mod 等の依存の有無
   - 関連する直近の git log（前提を壊した変更がないか）
3. 前提ごとに3分類で判定する
   - 一致（根拠 file:line）
   - 矛盾（根拠 file:line と、何がどう食い違うか）
   - 未確認（読めなかった理由）
4. 矛盾・未確認が1つでもあれば、「ユーザーに確認すべき一問」に絞って質問し、
   回答があるまで停止する
5. すべて一致なら「前提OK」と根拠一覧だけ報告して停止する。
   続けて実装やプランを勝手に始めない

## 実装・計画依頼から発動した場合

「実装して」「planして」等の依頼で先行発動した場合も、上記手順は同じ。
前提OK の報告、または矛盾への回答を得たあと、ユーザーの指示があってから
本来依頼された実装・プラン作成に進む。検証と着手を同一ターンで連続させない。

## 禁止

- 実装・ファイル編集・プラン作成へ進むこと
- 矛盾を「留意点」として報告へ埋め込み、確認せず続行すること
- 読んでいないものを「一致」と判定すること（推測は必ず「未確認」にする）
